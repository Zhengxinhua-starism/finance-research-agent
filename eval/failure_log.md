# 失败案例记录

> 这份文档记录**真实运行中发现的失败**，不是假想的风险清单。
> 每条记录必须包含：现象、根因、当时的处理、以及是否已修复。
> 未修复的条目保留在"已知局限"章节，不删除——
> 面试时被问到"这个系统有什么做不好的地方"，能答出具体案例比说"暂时没发现"有说服力得多。

## 记录格式

```
### F-{编号}｜{一句话现象}
- **发现时间**：YYYY-MM-DD
- **触发用例**：eval 用例 ID / 具体问题
- **现象**：实际输出是什么，期望输出是什么
- **根因**：定位到的具体原因（哪个模块、哪行逻辑）
- **trace**：traces/run_xxx.json（保留现场）
- **处理**：改了什么 / 为什么暂不改
- **状态**：已修复 / 已缓解 / 未修复（设计取舍）
```

## 已修复

### F-027｜上下文压缩在「最近 N 轮已超预算」时 0% 空转
- **发现时间**：2026-08-14（简历审查：从全部 trace 提取 80 次 compact 事件）
- **触发用例**：归因类长会话（工具 JSON 动辄 2000+ token）
- **现象**：平均压缩率 **2.7%**，最高 17.4%，大量事件压缩率为 0%。
  `should_compact()` 判定超预算并触发 compact，但输出 token 几乎不变。
- **根因**：旧策略把工具结果视为不可压（误以为 Gate 读 message content），
  且 `keep_recent_turns=3` + `context_max_tokens=3000`。
  `_partition` 发现 older 为空后直接 `return list(messages)`
  （`context_compact.py` 原 L140-151）。后续每一轮都会再触发一次无效压缩。
  实际上 Gate 只读 `evidence_pool` 里的 Evidence 对象（来自 `ToolResult.data`），
  消息历史里的工具 JSON 可以安全摘要。
- **处理**：
  1. 两条通路分离：Evidence 保精确数字，LLM 上下文按时间距离分层降保真度；
  2. 最近 1 轮完整保留，中间 2 轮工具结果做成关键指标摘要，更早轮次 LLM/规则摘要；
  3. 最近 1 轮仍超预算时，对 recent 的工具结果也做摘要，不再空转返回原文；
  4. `context_max_tokens` 3000 → 8000。
- **状态**：已修复。`eval_20260814_115957` 中 4 次 compact：平均压缩率 **72.8%**，最高 **86.5%**，0% 空转次数为 0。用例 4 token 49642 → 16831（-66%）。加权总分 0.912 → 0.923。

### F-022｜跨期对比证据只挂最新一期数字，补搜把工具目录全部打开
- **发现时间**：2026-08-13（全量评测用例 1）
- **触发用例**：用例 1「比亚迪 2025 年 ROE 是多少，相比 2024 年有什么变化」
- **现象**：预期 1 轮、2 个工具；实际 3 轮、11 个工具、286 秒。
  归因还缺「ROE 计算口径」说明。
- **根因（两层）**：
  1. `compare_periods` 的证据构造把三期合成一条，`numbers` 只保留最新值、
     `period_end` 只标最新一期。断言「2024 年 ROE = 21.7%」在门禁里找不到
     对应期数字 → 未验证率被顶过 0.3 → 触发补搜。
  2. 补搜 `allowed_tools = None`，等于把公告/研报/新闻/分部全部放开。
     证据池膨胀后 Verifier 抽出更多断言，未验证率继续高，跑满 3 轮。
- **处理**：
  1. 跨期对比按报告期切开，每期一条带该期全部指标的证据，另保留一条趋势摘要；
  2. 补搜按缺口关键词开放工具，不再打开全目录；
  3. 补搜判定的未验证率只统计带数字的断言（知识库定性断言按设计永远拿不到 ✅）；
  4. Planner 对 single_fact / cross_period 裁剪类型+主题之外的多余工具。
- **状态**：已修复

### F-023｜ROE 口径写在 source 字段，未进入证据正文
- **发现时间**：2026-08-13（全量评测用例 1）
- **触发用例**：用例 1
- **现象**：`FinancialMetrics.source` 已包含「ROE 口径：归母净利润 / 期末归母股东权益（摊薄）」，
  但研报通篇未说明口径，归因分被扣到 0.25。
- **根因**：证据构造只把 `metrics_display` 拼进 `content`，`source` 丢在 metadata 里。
  Verifier 和 Writer 只读 `content`，口径说明等于没写。
- **处理**：口径写入证据正文（核心指标证据 + 跨期切片证据），
  工具 interpretation 和杜邦 `to_display` 同步带上；Writer 杜邦框架强制要求引用口径。
  工具返回结构增加 `roe_scope`，缓存版本 2 → 3。
- **状态**：已修复

### F-024｜银行跨期题不检索行业框架，只能陈述营收利润背离
- **发现时间**：2026-08-13（全量评测用例 3）
- **触发用例**：用例 3「平安银行近三年的营业收入和净利润变化趋势如何」
- **现象**：事实分 0.90，归因分 0.00。报告承认无法归因，未提及拨备、非息、成本收入比。
- **根因**：`cross_period` 默认工具没有 `search_knowledge`，主题层也没有银行关键词映射。
  AKShare 通用利润表拿不到银行拨备/非息分项，知识库里的排查框架从未被召回。
  Writer 的 growth 框架只要求区分增速放缓与绝对值下降，没有要求解释背离。
- **处理**：银行主题命中即补 `search_knowledge`；知识库新增
  「银行营收与利润增速背离的归因框架」；Writer growth 框架要求背离必须给可能原因，
  分项数据缺失时标注为推测而不是省略。
- **状态**：已修复

### F-025｜`get_stock_price` 只打东财，本机代理下一律 ProxyError
- **发现时间**：2026-08-14
- **触发用例**：投资建议 / 行情类问题（如「能不能买入」「茅台行情如何」）
- **现象**：工具返回 `DataSourceError: stock_zh_a_hist: ProxyError ... push2his.eastmoney.com`，
  研报因缺少最新收盘价和区间涨跌而拒答或只能写「数据缺失」。
- **根因**：AKShare 的 `stock_zh_a_hist` 走东财历史 K 线，且 `requests` 会读取
  `HTTP_PROXY`。DeepSeek 需要代理，东财国内站被送进同一条代理后不可达。
- **trace**：`traces/run_a006e7c9be26_20260814_091809.json` 等多份
- **处理**：新增 `tools/price_history.py`，顺序 **腾讯 → 新浪 → 东财**，
  三路均 `httpx(trust_env=False)` 直连，不再把国内行情送进系统代理。
  公司简称也改从腾讯报价读取，不再依赖会被代理拦截的 `stock_individual_info_em`。
- **状态**：已修复

### F-001｜报告期列匹配到「公告日期」，年报筛选全部落空
- **发现时间**：2026-08-13（首次接真实 AKShare 接口）
- **触发用例**：所有涉及三大报表的用例
- **现象**：`get_income_history('002594')` 返回三行数据，报告期显示为
  `2026-04-29`、`2026-04-29`、`2026-03-28`，其中两行日期完全相同；
  日志出现 `未找到年报数据，退回使用全部报告期（同比口径将不准确）`。
  金额本身是对的，但混进了季报，同比变成了环比。
- **根因**：新浪三张报表的报告期列名是 **`报告日`**（值形如 `20241231`），
  而我的别名表写的是 `["报表日期", "报告日期", "报告期", "日期"]`。
  前三个都匹配不上，第四个 `日期` 走到"包含匹配"这一级时，
  命中了表里另一列 **`公告日期`**（值 `20260429`，是公告日不是报告期）。
  于是 `_select_annual_rows` 里的 `period.month == 12` 筛选全部失败，
  退回"取全部报告期"，把季报也当年报用了。
  这是个**静默失效**：不抛异常，金额也对，只有报告期是错的。
- **trace**：无（在接入真实接口的手工验证阶段发现，未走完整流程）
- **处理**：
  1. 新增 `REPORT_DATE_ALIASES = ("报告日", "报表日期", "报告日期", "报告期")`，
     把实际列名放在第一位；
  2. **删掉宽泛的 `日期` 别名**——这是根因。三段式匹配的"包含"级别
     对短别名过于危险，`日期` 会命中 `公告日期` / `更新日期`。
- **教训**：模糊匹配的别名必须足够长且有区分度。宁可漏匹配（会报错，能发现），
  也不要错匹配（不报错，很难发现）。
- **状态**：已修复

### F-002｜新浪利润表没有「扣非净利润」列，指标体系缺一块
- **发现时间**：2026-08-13
- **触发用例**：4（毛利率归因）、5（风险评估）—— 凡是用到扣非增速的
- **现象**：`IncomeRow.deducted_net_profit` 恒为 `None`，
  研报里扣非净利润显示"—"，风险规则"扣非净利增速 vs 营收增速背离（>10pp）"
  因数据缺失而**从不触发**——表现为"这家公司没有这个风险"，
  实际是"这条规则根本没跑"。
- **根因**：实测 `stock_financial_report_sina(symbol='利润表')` 返回 83 列，
  用 `'扣' in col or '非经常' in col` 扫描的结果是**空列表**。
  扣非净利润是交易所要求单独披露的指标，不在利润表主表科目里，
  新浪这个接口只返回主表科目。我在写别名表时假设它存在。
- **处理**：新增 `AKShareDataClient.get_abstract_metrics()`，
  从 `stock_financial_abstract` 取扣非净利润（该接口是转置表：
  行是指标、列是报告期，单位已是元），在 `_enrich_with_abstract()` 里
  按报告期合并进 `IncomeRow`。**只在字段为 None 时填充**，不覆盖报表原值——
  报表是一手来源，摘要是二手加工。
- **验证**：修复后 002594 三期扣非分别为 294.46 / 369.83 / 284.62 亿元，
  风险规则 5「扣非净利润增速与营收增速背离」正常触发。
- **教训**：`detect_risk_alerts` 里"数据缺失就跳过规则"的设计是对的
  （不能把"没查"说成"没风险"），但如果没有 `unavailable_data` 字段
  显式暴露出来，缺失会被当成"检查通过"。这个字段救了这次排查。
- **状态**：已修复

### F-011｜日期解析漏掉带时分秒的格式，新闻时间窗过滤完全失效
- **发现时间**：2026-08-13（改新闻检索顺序时顺带发现）
- **触发用例**：所有调用 `search_news` 的用例（4、6 等归因类问题）
- **现象**：`search_news(ticker='002594', days=30)` 和 `days=2`
  返回**完全相同的 3 条**新闻，且每条的 `published_at` 都是 `null`。
  时间窗参数形同虚设——问"最近两天有什么消息"会拿到几个月前的内容。
- **根因**：东财新闻接口的「发布时间」是 `"2026-08-13 10:30:00"`（带时分秒），
  而 `parse_report_date` 只有两条路径：
  (a) 提取全部数字，长度 == 8 才解析 → 这里提取到 14 位数字，不等于 8，跳过；
  (b) 用 `%Y-%m-%d` 等格式整串匹配 → 多了时间部分，全部失败。
  于是返回 None。所有条目落进"无日期"桶，被 `MAX_UNDATED_ITEMS=3` 截断成 3 条，
  两个不同的 days 参数自然返回同一批。
- **处理**：改成用正则提取"年-月-日"三段，不再要求整串完全匹配某个格式。
- **二次踩坑**：第一版正则用了宽泛的 `\D{0,3}` 做分隔符，
  结果 `"2024年第13期"` 被回溯匹配成 `2024-01-03`——一个**看起来合法的假日期**。
  这比返回 None 危险得多：假日期会成为证据的 `disclosure_date`，
  直接影响前视偏差判定。改成限定字符类 `[-/.\s年]` 后修正。
- **验证**：11 个格式用例全通过；实测 `days=30` 得 10 条、`days=2` 得 1 条，
  时间窗生效。
- **教训**：与 F-001 同源——**模糊匹配要收紧，宁可漏也不要错**。
  漏匹配会报错或返回 None（能发现），错匹配会产出合理但错误的值（发现不了）。
- **状态**：已修复

### F-022｜来源体系缺第二层，券商研报与公众号传闻同等对待
- **发现时间**：2026-08-13（对照同花顺的三层可靠性模型复盘）
- **现象**：`SourceType` 里 `news` 一个类型同时装着券商研报和公众号传闻，
  两者都是 priority 10、都最高只能拿 ⚠️未验证。这既低估了前者
  （有署名、有方法论的机构分析），也高估了后者（无来源的市场猜测）。
  另外 `announcement`（公告）有类型定义，但**没有任何数据源产出它**——
  第一层里只有数字，没有文字。
- **具体后果**：知识库里明确写了归因排查要"检查是否有一次性减值、
  会计政策变更、合并范围变化"，但这些信息不在三大报表的数字里、只在公告里，
  没有数据源就永远无法执行这条排查。
- **处理**：
  1. 新增 `research_report` 来源类型（priority 40，介于行情 50 与知识库 30 之间）；
  2. 引入 `SOURCE_TIER` 三层映射，把 9 种来源类型归并成
     ①已披露事实 / ②机构判断 / ③待验证信息。
     优先级是给**门禁**用的连续排序，层级是给**读者**用的离散判断，
     两者用途不同不能混用——9 个数字对读者没有意义，3 个层级有；
  3. `is_official` 改为由层级决定（只有第一层为 True），
     确保**研报最高只能拿 ⚠️未验证**——机构判断再权威也是判断不是事实；
  4. 新增两个工具：`get_disclosure_events`（公告 + 业绩预告，第一层）、
     `get_analyst_coverage`（券商研报，第二层）；
  5. 研报来源表新增「可信度层级」列并附层级说明。
- **护栏设计（这次最需要想清楚的地方）**：
  `stock_research_report_em` 返回「东财评级」（买入/增持）和三年期盈利预测。
  这两类内容如果进证据池，Writer 完全可能引用它们——等于从后门绕过
  F-017 刚建立的"不提供投资建议"护栏。因此在**解析阶段**就丢弃，
  只保留机构名、报告标题、日期。保留标题是因为标题本身承载分析判断
  （"销量环比改善，出口再创新高"），这才是第二层来源的价值。
  实测核验：`recent_reports` 的字段只有 date/industry/institution/title，
  字段名与字段值均无评级/目标价泄漏，生成的证据 `numbers` 全为空。
- **一并调整的行为**：`market_data` 归入第一层，因此行情类断言
  （收盘价、区间涨跌幅）现在可以拿 ✅已验证，此前被降级为 ⚠️。
  理由是收盘价与营收一样是客观可核验的事实，此前的降级过度保守。
- **未采纳的来源**：交易所互动平台（大量"股价何时涨"提问，信噪比过低）、
  盈利预测接口（对未来的预测，与"整理已披露信息"定位冲突）、
  机构调研明细（AKShare 只有统计没有纪要内容）。
  TradingAgents 的 reddit/stocktwits/polymarket/fred 也全部未采纳——
  那是美股交易决策系统的数据结构，情绪与预测市场数据会直接冲淡
  "每条结论可追溯到披露文件"这个核心定位。
- **状态**：已完成

### F-021｜缓存键不含返回结构版本，改了工具字段后旧缓存静默供应旧结构
- **发现时间**：2026-08-13（跑用例 4 评测时发现）
- **现象**：给 `IncomeRow.to_display()` 补齐了期间费用、利润构成等约 20 个字段，
  单元测试里数据都对，但评测跑出来研报仍然写"缺乏其他期间费用数据"。
  直接调工具检查，返回的 `periods` 里费用字段一个都没有，只有 `rd_expense`。
- **根因**：缓存键由「工具名 + 参数哈希」构成，**不含返回结构的版本**。
  改的是返回结构、没改参数，键因此完全一致，磁盘缓存（TTL 1 天）
  继续供应改动前的旧 payload。清掉 25 条缓存后字段立刻全部出现
  （文本从 2205 字符涨到 4344 字符）。
- **危害**：完全静默。不报错、不告警、数据看起来也"有"，
  只是新增的部分永远到不了 LLM 面前。如果不是评测里那条
  "缺失期间费用率"的判定，这个问题会一直潜伏——
  而且会让人误以为是提示词或 Writer 的问题，往错误方向排查。
- **处理**：缓存键加入 `TOOL_RESULT_SCHEMA_VERSION`，
  格式变成 `tool:{name}:v{版本}:{hash}`。**改任何工具的返回字段都必须 +1。**
  版本号放进键而不是放进值：放值需要先读出旧数据才能判断是否过期，
  放键则旧条目直接不被命中，随 TTL 自然淘汰，无需清理逻辑。
  `session/cache.py` 的异步层同步改造——两层共用同一套 key 格式是
  双客户端设计成立的前提，只改一边会让两层各存各的。
- **教训**：这是本项目第四类"静默失效"（前三类是别名失配 F-001/F-013、
  抓到未输出 F-019、日期解析 F-011）。共同特征是**功能没生效但系统不报错**。
  能发现它们靠的都是评测里那条具体的失败判定，而不是人工review——
  这反过来印证了 F-020 里把评测标准写细的价值。
- **状态**：已修复

### F-019｜研报"用数字解释数字"，归因没有业务信息量
- **发现时间**：2026-08-13（与同花顺问财输出对比）
- **现象**：问"净利润为什么下降"，研报的回答是"因为毛利率下降了 1.70pp、
  营收增速放缓"。这只是把同一件事换个说法讲两遍，读者看完不知道
  经营上发生了什么。核心结论区还退化成 24 条原子事实的流水账
  （"2025年营业成本为6613.05亿元"——这不回答任何问题）。
- **根因（三层，缺一不可）**：
  1. **数据层**：没有分部数据就无法区分"业务结构变化"与"经营恶化"；
     期间费用抓了没输出；利润构成科目完全没接。Writer 想做业务归因
     但手上只有整体指标，只能拿指标互相解释；
  2. **Verifier**：提示词要求抽"完整、独立、可核查的陈述句"，
     模型就老实抽成一个数字一条，产出的是数据点清单而非论断；
  3. **Writer**：提示词只规定了格式和禁止事项，没有要求业务归因，
     也没有要求区分主因次因。
- **处理**：
  1. 数据层补齐（见 `docs/data_coverage.md` 已完成清单），
     其中分部数据的**结构效应分解**是关键——实测比亚迪 2025 年
     结构效应仅 +0.17pp、自身效应 −1.87pp，直接回答了
     "是业务结构变了还是各业务自身在恶化"；
  2. Verifier 提示词加"抽论断不抽数据点"的正反例，并给出数量指引
     （6~12 条合理，超过 20 条基本是在罗列）；
  3. Writer 提示词加"不要用数字解释数字"的判据与正反例，
     要求按贡献大小区分主因次因，无法证实的归因必须标注为推测；
  4. Planner 的 causal 类工具集补上 `search_news`、`get_segment_breakdown`、
     `get_operating_efficiency`——此前 causal 类根本不调新闻，
     Writer 连外部因素的信息来源都没有。
- **仍拿不到的**：销量、单车利润、研发资本化率流量、折旧摊销明细，
  这些是 AKShare 的硬边界，研报中如实声明而非假装不重要。
- **状态**：已修复（数据与提示词层面，效果需跑评测确认）

### F-020｜评测只检查数字，测不出归因质量
- **发现时间**：2026-08-13
- **现象**：v1 的 `expected_facts` 只检查"有没有报出正确的 ROE/毛利率数值"。
  一份把所有数字都报对、但通篇"净利润下降因为毛利率下降"的研报能拿高分——
  而这恰恰是实际输出最大的质量问题。评测测不出真正想改进的东西。
- **处理**：测试集升到 v2，评测维度从 4 个增加到 5 个。
  1. 新增 `attribution_quality` 维度（权重 0.25，仅次于事实准确性），
     用独立的 Judge prompt 评审，与事实评审**分开调用**——
     合在一起会让模型被数字的正确性带偏；
  2. 用例新增三个字段：`attribution_requirements`（必须给出的业务层面原因）、
     `forbidden_patterns`（用数字解释数字等坏习惯，每命中一条扣 0.15）、
     `good_answer_example` / `bad_answer_example`（给 Judge 一个可对照的标尺）；
  3. 总分改为**只对适用维度归一化加权**：拒答题不评事实准确性，
     单点事实题没有归因要求，用 N/A 维度参与加权会无谓稀释分数；
  4. 与事实评审同样的做法：不信任 LLM 自己算的分数，用判定列表在代码里重算。
- **验证**：权重设计达到预期——"数字略差(0.7)但归因好(0.9)"得 0.885，
  高于"数字全对(0.9)但归因差(0.2)"的 0.77。这个排序关系正是想要的导向。
- **状态**：已完成（评测标准本身，实际分数需跑完才有）

### F-018｜门禁对跨期/跨表断言系统性误判，同一问题两次运行结果天差地别
- **发现时间**：2026-08-13
- **现象**：同一个问题"比亚迪2025年净利润为什么下降"跑两次：
  - 第一次：24 条断言**全部** ✅，未验证率 0.0%；
  - 第二次：15 条断言只过 5 条，未验证率 66.7%，核心数据（归母净利润、
    毛利率、净利率）全变 ❌拒答，而且触发了 3 轮补搜（多花 220 秒）。
  数据是同一批年报数据，门禁是确定性代码，结果却随机。
- **根因**：门禁的**确定性没问题，非确定性来自它的输入**。
  `ClaimNumber` 的指标命名空间没有期间维度，而 `_check_numbers` 又要求
  **单条证据覆盖断言里的全部指标**。于是断言的表述形态决定了成败：
  1. **跨期对比断言**——"毛利率由2024年的19.44%降至2025年的17.74%"
     产生两个 metric 都是 `gross_margin` 的数字，任何单条证据只能满足一个，
     另一个必然报 mismatch。而这恰恰是归因分析最常见的句式；
  2. **跨表复合断言**——"营收X、净利Y、经营现金流Z"，营收和净利在利润表、
     现金流在现金流量表，本来就分属两条证据，不存在能同时覆盖的单条证据。
  LLM 每次抽取时是产出原子事实还是对比句式是随机的，于是结果随机。
- **附带的误导**：跨表场景下报的是
  `net_profit 声称326.19 vs 原始402.54`——但 net_profit 在 2025 年报里
  明明对上了，真实问题是 `operating_cashflow` 没被覆盖。
  旧实现在找不到全覆盖证据时会退而求其次去匹配另一期，然后报一个
  与真实问题无关的差异，把排查引向错误方向。
- **处理**：
  1. `ClaimNumber` 增加 `period` 字段（"2025" 或 "2025-12-31"），
     Verifier 提示词要求跨期对比时必填；
  2. 重写 `_check_numbers`：**串期防护由"报告期"承担，不再由"单条证据"承担**。
     - 带 period 的数字 → 只在该期的证据里核对（支持跨期对比）；
     - 不带 period 的数字 → 整组必须落在同一期，期内允许跨证据组合
       （解决跨表问题），优先选覆盖最完整的期，其次最新期；
  3. `_match_one` 在同一指标被多条证据覆盖时**优先取能对上的那条**——
     不同来源可能有口径差异（如 ROE 摊薄 vs 平均），有一条口径对得上
     就说明数字有依据，不该因另一条口径不同判为造假；
  4. 指标找不到时明确报"以下指标在证据池中找不到对应数据: XXX"，
     不再拿无关差异搪塞。
- **验证**：7 个场景全部符合预期——单期单指标、跨期对比、跨表复合、
  省略期间自动落最新期都放行；真错数字、串期造假仍被拦截；
  指标缺失给出准确原因。
- **遗留（不算 bug，但要知道）**：绝对值 5% 容差意味着相邻两年数值相差
  小于 5% 的指标无法靠数值区分。实测比亚迪营收 2024=7771.02亿、
  2025=8039.65亿，仅差 3.34%，把 2024 的值标成 2025 期也能通过。
  净利润（差 19%）、毛利率（差 1.7pp）不受影响。
  收紧到 1% 更贴近真实的四舍五入误差（实测四舍五入偏差 < 0.01%），
  但会否引入新的误拦需要跑评测确认，暂不改。
- **状态**：已修复

### F-015｜断言被强贴会话股票代码，导致跨标的误比对、正确结论被错杀成拒答
- **发现时间**：2026-08-13
- **触发场景**：UI 里选了 002594（比亚迪），但问题问的是"茅台行情如何"。
  Retriever 正确地去取了 600519 的行情，证据池里同时有两家公司的数据。
- **现象**：研报里 5 条关于茅台的结论**全部**被判 ❌拒答，理由是
  `latest_close 声称 1355.99 vs 原始 89.78`、
  `period_return 声称 0.0569 vs 原始 -0.0362`。
  89.78 是**比亚迪**的收盘价——门禁拿比亚迪的股价去核对茅台的股价。
- **根因**：`VerifierAgent._to_claim(extracted, as_of, ticker)` 里的 `ticker`
  是会话级的目标公司代码，被无条件贴到**每一条**断言上：
  ```python
  ticker=ticker or None      # ticker 恒为 state["ticker"] = "002594"
  ```
  于是"茅台收盘价 1355.99"这条断言的 `claim.ticker` 变成 002594。
  `EvidenceGate._find_candidate_evidence` 里的标的过滤
  （`claim.ticker != evidence.ticker → continue`）把 600519 的证据全滤掉了，
  只剩比亚迪的证据能匹配 `latest_close` 这个指标名 → 数字当然对不上。
- **危害等级高**：这不是漏报而是**误杀**。门禁本身工作正常，
  数据也拿对了，但因为标的归属错误，把本可以正常输出的结论
  打成了 ❌拒答，还给出一个完全误导的理由（让人以为数据源有问题）。
- **处理**：
  1. `ExtractedClaim` 增加 `ticker` 字段，由 LLM 指明每条断言描述的是哪家公司；
  2. `_to_claim` 改为「断言自报优先，会话代码兜底」，绝不反向覆盖；
  3. 加 `_normalize_claim_ticker()` 处理模型填公司名（"贵州茅台"）
     或带前缀（"SH600519"）的脏值——脏值直接塞进 `Claim.ticker`
     会让门禁过滤掉**所有**证据，比不填更糟。
- **验证**：同样的证据池，修复后该断言判为 `unverified`
  （行情数据属非官方披露，⚠️ 是正确语义），不再是 `number_mismatch`。
- **状态**：已修复

### F-016｜指标名被硬塞，单日涨跌幅当成区间涨跌幅
- **发现时间**：2026-08-13（与 F-015 同一次运行）
- **现象**：`2026-08-10贵州茅台股价上涨3.03%` 这条断言，
  被抽成 `period_return = 0.0303`，然后与证据里的
  `period_return = -0.0362` 比对失败。
- **根因**：`period_return` 在证据里的含义是**整个查询区间**的累计涨跌幅，
  而模型想表达的是**某一天**的涨跌幅。允许的指标名列表里没有"单日涨跌幅"，
  提示词也没说找不到对应指标时该怎么办，模型就近塞进了语义相似但不同的字段。
- **处理**：提示词里补三条——
  (a) 明确 `latest_close` / `period_return` / `daily_volatility` 的确切含义；
  (b) 找不到语义完全对应的指标名时，**把该数字从 numbers 里省略**
      （断言文本保留，作为定性断言核查），或干脆不抽这条断言；
  (c) 说明硬塞的后果就是必然报「数字不一致」，把正确内容错杀成拒答。
- **状态**：已修复（提示词层面，需实跑观察效果）

### F-017｜索取投资建议的问题没被识别，拒答理由驴唇不对马嘴
- **发现时间**：2026-08-13
- **现象**：问题"茅台行情如何了，**推荐什么价为入**"跑完了完整流程
  （146 秒、44k token、9 次 LLM 调用、3 轮 Verifier），最终拒答，
  但给出的理由是"数字与来源不一致"，建议是"确认股票代码是否正确"。
  实际上股票代码完全正确，真实理由是**这个问题在索取投资建议**——
  而这个判断看一眼问题就能下，不需要任何数据。
- **根因（两层）**：
  1. 系统没有"职责范围"这个概念。Writer 的 prompt 里禁止输出投资建议，
     但那是**输出端**的约束；**输入端**从不判断问题该不该答，
     于是一个注定拒答的问题也要走完整个研究流程。
  2. 拒答报告的"建议"章节是三条写死的模板，与实际失败原因无关。
     给出与现实不符的排查建议，比不给建议更糟——会把人引向错误方向。
- **处理**：
  1. Planner 增加 `is_out_of_scope()`，用明确索取交易动作的关键词判定

     刻意不把单独的"建议"算进去——"建议关注哪些指标"是合法的方法论问题；
  2. `ResearchPlan` 增加 `out_of_scope` 字段；
     Graph 在 planner 后加条件边 `should_start_research`，
     超范围问题直接跳到 writer，**跳过检索与核查**；
  3. Writer 增加 `_build_out_of_scope_report()`，与"证据不足"型拒答分开。
     两者对用户的含义完全不同：前者是"这个问题我不该回答"，
     后者是"这个问题我答不了"，混为一谈会让用户以为补数据就能拿到买卖建议。
     报告里同时给出"本系统能做什么"和四条改写示例；
  4. 证据不足型拒答的建议改为按实际 `gate_status` 生成
     （number_mismatch / lookahead_blocked / unverified 各有对应建议）。
- **附带收益**：这类问题从 146 秒降到约 4 秒（只跑 Planner 的关键词判定，
  连 LLM 都不调）。
- **状态**：已修复

  - 第三层（待做）：工具按维度重组而非按接口，换数据源时 Agent 侧不感知。

### F-012｜新闻检索顺序反了：先调付费源再降级到免费源
- **发现时间**：2026-08-13（需求调整）
- **原实现**：配了 `TAVILY_API_KEY` 就先调 Tavily，失败或空结果才降级到 AKShare。
- **问题**：
  1. **成本**：Tavily 按次计费，而绝大多数查询 AKShare 就够了，
     每次都先付费调一遍是纯浪费；
  2. **精度**：AKShare 东财新闻是按股票代码**精确关联**的，
     Tavily 是关键词搜索，可能召回同名或同行业的无关公司；
  3. **语义**：两者是**补充**关系而非**替代**关系，
     "降级"的框架下只会用其中一路，白白丢掉另一路的结果。
- **改成**：AKShare 打底 → 条数不足（< `config.news_min_results`，默认 3）
  且配了 key → 调 Tavily 补充 → 两路合并去重（URL 优先，退回归一化标题）。
- **附带修的一个隐患**：原来两路都失败时会静默返回空列表，
  LLM 会把它读成"该公司近期无重大事件"。现在区分三种情况——
  所有数据源都抛异常才抛 `DataSourceError`；
  正常返回 0 条时在 `retrieval_notes` 里写明原因，
  并在 `usage_note` 里明确提示"请勿据此推断无重大事件"。
- **状态**：已修复

### F-003｜ROE 降级路径混用了两种口径
- **发现时间**：2026-08-13（修 F-002 时顺带发现）
- **现象**：自算 ROE（002594 / 2024 年）= 402.54 / 1852.51 = **21.73%**，
  而财务摘要接口给的 `净资产收益率(ROE)` = **26.05%**，差 4.3pp。
- **根因**：两个都对，但**口径不同**：
  - 自算：归母净利润 / **期末**归母股东权益（摊薄口径）；
  - 摘要：归母净利润 / **期初期末平均**净资产，且分母**剔除了其他权益工具**
    （永续债等，002594 该项为 148.94 亿）。
    验算：402.54 / (1852.51 - 148.94) = 23.63%，正是摘要里的"摊薄净资产收益率"；
    再用平均净资产则得到 26.05%。
  原本我写的降级逻辑是"资产负债表拿不到时用摘要 ROE"，注释里还写着
  "口径一致，可以直接替代"——这个判断是错的。
- **处理**：保留降级（有个数总比没有强），但把口径差异写进
  `FinancialMetrics.source` 字段，研报里会显示
  "ROE 口径：净资产收益率（平均口径，来自财务摘要；资产负债表获取失败）"。
- **为什么不统一成一种**：平均净资产口径更严谨，但需要多拉一期资产负债表
  （见 F-007 同类权衡）。当前选择是"用摊薄口径 + 显式声明"，
  而不是"偷偷混用两种口径"。后者才是真正的问题。
- **状态**：已缓解（口径已披露，未统一算法）

### F-004｜毛利率用 5% 相对容差导致门禁形同虚设
- **发现时间**：待记录
- **触发用例**：4（比亚迪毛利率趋势）
- **现象**：LLM 写"毛利率 22.9%"，真实值 21.8%，
  证据门禁判为 `verified`（相对误差 5.0%，刚好卡在容差内）。
  但 1.1 个百分点的毛利率差异在投研上是完全不同的结论。
- **根因**：`EvidenceGate` 早期对所有数字统一用 `number_tolerance=0.05`
  的相对误差。对金额（营收 7771 亿 vs 7770 亿）这个容差合理，
  对比率则过于宽松。
- **处理**：按数字语义分三档容差——绝对值 5% 相对误差、
  比率 0.5 个百分点、同比增速 1 个百分点。
  实现见 `harness/evidence_gate.py` 的 `_compare()` 和 `infer_number_kind()`。
- **状态**：已修复

### F-005｜上下文压缩后 API 返回 400（tool 消息失配）
- **发现时间**：待记录
- **触发用例**：归因类问题，检索轮次较多时
- **现象**：ReAct 循环跑到第 5~6 轮时，DeepSeek 返回
  `400: messages with role 'tool' must be a response to a preceding message with 'tool_calls'`。
- **根因**：`ContextCompact` 压缩时把发起 `tool_calls` 的 assistant 消息
  归为"过程性对话"压掉了，但它对应的 `role=tool` 消息因为
  "保留所有工具结果"的规则被留下，形成孤儿消息。
- **处理**：两处修改——`_is_evidence_bearing()` 把带 `tool_calls` 的
  assistant 消息也算作"携带证据"予以保留；
  另外加一道 `_repair_tool_call_pairing()` 做兜底，剔除失配的 tool 消息。
- **状态**：已修复

### F-007｜杜邦分析用期末总资产而非平均总资产
- **发现时间**：设计阶段已知
- **现象**：资产规模快速扩张的公司（如比亚迪 2022-2023），
  用期末总资产算出的资产周转率偏低，杜邦拆解的因子贡献判断可能偏移。
- **根因**：AKShare 单次调用拿不到期初数，取平均值需要多拉一期数据，
  增加一次网络请求和一次可能的失败点。
- **处理**：接受这个近似，但在两处显式声明口径：
  `data/schemas.py` 的 `compute_dupont()` 文档字符串，
  以及研报底部的"口径说明"区块。
- **残留问题**：对资产规模年增速超过 40% 的公司，
  周转率的偏差可能达到 15% 以上，影响"哪个因子主导"的判断。
- **状态**：已缓解（口径已披露，未改算法）

## 未修复（设计取舍）

### F-008｜披露日期是估算值，不是真实披露日
- **现象**：证据的 `disclosure_date` 用法定披露截止日（年报=次年 4/30）估算，
  而不是该公司实际的披露日期（可能是 3/28）。
- **影响**：分析基准日落在真实披露日与法定截止日之间时
  （例如 as_of_date=2025-04-10，公司 3/28 已披露年报），
  前视偏差检查会**误拦**一条本可使用的数据，结论被降级为 ❌拒答。
- **为什么不改**：获取真实披露日需要爬取交易所公告或接入付费数据源，
  成本远超收益。而且这个偏差的方向是**保守的**——
  宁可误拦一条合规数据，也不能让未来数据混进历史分析。
  在投研场景里，这两种错误的代价不对称。
- **状态**：未修复（有意为之）

### F-009｜只取年报，忽略季报和中报
> **2026-08-13 修正**：下面"范围外"的判断有误。当时以为季度数据难以获取，
> 实际上 `stock_profit_sheet_by_report_em`（203 列）直接返回季度报告期
> （实测含 2026-03-31、2025-09-30、2025-06-30）。
> 真正的工作量在"同比期匹配"逻辑，不在数据获取。
> 已改列为 P2 待办，见 `docs/data_coverage.md`。

- **现象**：`_select_annual_rows()` 只挑月份为 12 的报告期。
  问"最新一个季度的营收"会拿到上一年的年报数据。
- **为什么不改**：md 的指标体系（营收增速、毛利率同比）全是同比口径，
  混入季报会让"上一期"变成上一季度，同比变环比，
  算出的增速在业务上没有意义。要正确支持季度分析需要
  单独的"同比期匹配"逻辑（2024Q3 对 2023Q3），
  这是一个独立的功能而非 bug 修复。
- **状态**：未修复（范围外）

### F-010｜新闻工具的信息质量不稳定
- **现象**：AKShare 东财新闻返回的内容常常是行情快讯甚至同行业公司的报道，
  而非该标的的深度分析，对归因帮助有限。
- **为什么不彻底改**：新闻在证据体系里本来就是最低等级（`source_type="news"`，
  最高只能标 ⚠️未验证），它的作用是"提供分析线索"而非"提供证据"。
  为提升它的质量投入成本，收益低于优化财报数据的解析。
- **已做的缓解**：把检索策略从"Tavily 优先 → 失败降级 AKShare"改成
  "AKShare 打底 → 条数不足（< 3）→ Tavily 补充"，详见 F-012。
- **状态**：已缓解（质量问题仍在，但成本与召回的平衡更合理）

### F-026｜用例 6（茅台净利率归因）attribution 0.50，不是知识库没召回
- **发现时间**：2026-08-14（全量评测 `eval_20260814_102132`，全量最低分）
- **触发用例**：用例 6「贵州茅台的净利率为什么能维持在这么高的水平」
- **现象**：加权 0.7675，`attribution_quality` 0.50，`evidence_coverage` 0.50。
  Judge 评语：费用率/产品结构贡献/品牌溢价均标 ⚠️，商业模式浅尝辄止，
  未深入供需关系与渠道控制力；期间费用率只有定性、没有具体数字。
- **trace**：`traces/run_67ccee9da6bb_20260814_101552.json`
- **根因（不是 RAG 没召回，是「召回了但写不进 ✅」）**：
  1. `search_knowledge` **已经命中**「白酒行业分析框架」（rank 1，`sector=baijiu`），
     查询词含品牌溢价 / 产能稀缺性 / 提价能力。
  2. 定性断言「高净利率由品牌溢价支撑」匹配到来源「知识库：白酒行业分析框架」，
     但 `source_type=knowledge_base` 按设计 `is_official=False`，最高只能 ⚠️，
     门禁输出 `unverified: 定性断言，来源为非官方渠道`。
  3. 8 次门禁拦截 4 次。分部数据工具调用了，但「茅台酒贡献绝大部分收入」
     仍被判「无来源支撑」——断言没挂上 `get_segment_breakdown` 的 Evidence。
     费用端断言没有数字，`get_financial_metrics` 未调用（预期工具 3/4）。
  4. Planner 给这道 causal 净利率题选了 `framework=dupont`，和白酒品牌/渠道
     框架错位；Writer 核心结论里「为什么高」几乎全是 ⚠️，详细分析不敢展开。
- **处理**：暂不改门禁规则（知识库拿不到 ✅ 是有意的，避免把行业常识当成公司事实）。
  面试时承认：这是「证据等级」和「归因深度」的张力——Judge 要商业模式，
  门禁不允许把知识库写成已验证事实。后续可考虑：Writer 把知识库框架显式
  标成「行业研究观点」而不是省略；Planner 对白酒净利率题改用 profitability 框架；
  费用率从利润表 `period_expense_ratio` 抽数字，减少无数字的定性断言。
- **状态**：未修复（设计张力，已定位）
