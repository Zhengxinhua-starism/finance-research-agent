# 面试问答准备

按面试官最可能追问的顺序组织。每题给出**回答要点**和**如果被继续追问该怎么答**。
不要背稿，要能对着代码指出具体位置。

---

## 一、架构判断力

### Q1：为什么有些用框架，有些自己写？

**要点**：分界线画在"通用问题 vs 领域特有问题"，不是"简单 vs 复杂"。

- 编排（谁在什么条件下跑、状态怎么合并、条件回边）→ LangGraph。
  这是标准化问题，成熟方案够用，自建没有额外价值。
- 运行时（ReAct 循环、max_turns、上下文压缩、证据门禁）→ 自建。
  这是项目的差异化所在，藏进框架配置里既讲不清也改不动。

**追问：具体哪里改不动？**

举 `create_react_agent` 的例子：
1. max_turns 耗尽时它抛异常，而我需要"返回已获得的证据 + 输出降级研报"——
   一份带 ⚠️ 标注的不完整研报，比一个 500 错误对用户有价值得多；
2. 上下文超限时它直接报 API 错误，没有"保留工具结果、只压缩对话"这个策略位；
3. 证据门禁根本无处安放，它不是 LangGraph 的概念。

**追问：那 LangGraph 给你带来了什么？**

三样：`StateGraph` 的条件边（补搜回路）、reducer 机制
（`evidence_pool` 的去重累加、`retrieval_count` 的原子累加）、
`recursion_limit` 的死循环保护。这三样自己实现要小心处理并发和重试语义，
不划算。

---

### Q2：白板画一下 ReAct 循环

```
messages = [system, user]
turn = 0
while turn < max_turns:
    turn += 1
    ① 压缩检查：token 超阈值 → 压缩（保留 system/最近3轮/所有工具结果）
    ② 最后一轮：撤掉 tools 定义 + 追加"立即给结论"指令
    ③ 调 LLM(messages, tools)
    ④ 无 tool_calls → status="completed"，返回
    ⑤ 有 tool_calls → 并发执行工具 → 结果（含失败）全部回填 messages
    ⑥ token 累计超上限 → status="token_limit"，返回
轮次耗尽 → status="max_turns"，返回（保留已有工具结果）
```

四种 status：`completed` / `max_turns` / `token_limit` / `error`。

**追问：为什么失败的工具结果也要回填？**

让模型看见 `[工具执行失败] get_cash_flow: timeout`，它会自己换工具或说明数据缺失。
静默跳过的话，模型会以为工具返回了空数据，然后基于"空数据"编造结论。
这是把"自愈能力"还给 Agent。

**追问：为什么最后一轮要撤掉 tools？**

否则模型会在最后一轮又发起工具调用，但已经没有下一轮去执行了，
这一轮的输出就是纯粹的浪费。撤掉 tools 定义还能省一部分 prompt token。

**追问：token 检查为什么放在调用之后？**

放在之前需要精确预估请求体大小，而 API 返回的 usage 是权威值。
代价是多花一次调用的钱，换来判断准确。

---

### Q3：LangGraph 的状态怎么设计的？

用 `TypedDict` + `Annotated` reducer，不用 Pydantic BaseModel。

**为什么不用 Pydantic**：LangGraph 要求状态支持"节点返回部分字典"的增量更新。
Pydantic 模型需要全量构造，节点会写成 `state.model_copy(update={...})`，
啰嗦且容易漏字段。

**三个自定义 reducer**：
- `evidence_pool`：`merge_evidence` 累加 + 按指纹去重。
  用默认覆盖语义的话，第二轮检索会冲掉第一轮的证据；
  用 `operator.add` 又会在缓存命中时堆积重复证据。
- `retrieval_count`：`operator.add`。节点只返回增量 `1`，
  不做"读旧值再写新值"——那在重试场景下会丢更新。
- `errors` / `node_path`：`operator.add` 累加，不覆盖。

## 二、幻觉与非确定性

### Q4：怎么防止模型编数字？

三级证据门禁（`harness/evidence_gate.py`），核心是**职责切分**：

- LLM 负责**抽取**：把自然语言组织成结构化断言 + 数字
  （`{metric: "gross_margin", value: 0.218, kind: "ratio"}`）；
- 代码负责**判定**：数字比对、日期比较、来源等级——全是确定性计算。

```
第1级 来源  证据池里有没有支撑这条断言的来源？   → 无 → ⚠️未验证
第2级 时点  披露日期 ≤ 分析基准日？             → 否 → ❌lookahead_blocked
第3级 口径  合并报表 vs 母公司报表有没有混用？   → 混用 → ⚠️未验证
第4级 数字  断言里的数字与来源一致？            → 否 → ❌number_mismatch
```

**追问：为什么不让 LLM 自己检查一遍？**

用非确定性系统校验非确定性系统，幻觉会叠加。而且模型对自己的输出天然自信，
self-critique 往往只会确认原答案。数字比对和日期比较是确定性的，就该用代码做。

**追问：容差怎么定的？**

分三档，这是最容易被追问的点：
- 绝对值 5% 相对误差——容忍"7771 亿 vs 777.1 亿元"这类单位换算和四舍五入；
- 比率 **0.5 个百分点**——21.8% 和 22.9% 的相对误差正好 5%，
  按统一容差会通过，但在投研上是完全不同的结论；
- 增速 1 个百分点，同理。

一刀切 5% 会让比率类校验形同虚设。这个坑我在 `eval/failure_log.md` 的 F-002 里记了。

### Q5：什么时候拒答？拒答和"不确定"有什么区别？

借鉴 ai-hedge-fund 的弃权语义：**abstain ≠ neutral**。
"查不到证据"不等于"证据表明不成立"，更不等于"中性判断"。

所以 `GateResult` 没有 True/False，只有四种状态，
调用方在类型层面就无法把"查不到"误读成"没问题"。

映射到研报三级标注：
- `verified` → ✅已验证
- `unverified` → ⚠️未验证
- `number_mismatch` / `lookahead_blocked` → ❌拒答

**追问：为什么数字对不上要拒答，不是标未验证？**

`unverified` 的语义是"存疑但可以写"，`number_mismatch` 的语义是
"模型算错或编造了数字"，`lookahead_blocked` 是"存在前视偏差"。
后两者都属于"这句话不能出现在研报里",跟"存疑"是两回事。

**追问：Writer 会不会把 ⚠️ 改成 ✅？**

碰不到。研报的"核心结论"清单和"数据来源"表格是**代码直接渲染**的，
LLM 只写"详细分析"正文。即使它在正文里写了没依据的话，
读者对照两个确定性区块就能立刻发现。

### Q6：处理非确定性做了哪些事？

分三类：

**超时保护**
- 工具级 30s（`ThreadPoolExecutor` + `future.result(timeout)`，
  不用 `signal.alarm`——它只能在主线程用，FastAPI 的同步端点跑在工作线程里）；
- LLM 级 120s + 连接超时 10s；
- 循环级 max_turns=10 + token 上限 120k。

**失败分类**
- 工具错误分四类：`tool_not_found` / `param_error` / `execution_error` / `timeout`；
- LLM 重试只对**可重试错误**生效：429、5xx、网络超时。
  400（参数错）和 401（鉴权失败）重试三次只是把同一个错误犯三遍还浪费 14 秒。

**降级路径**（完整清单见 `docs/architecture.md` 第 11 节）
每个组件都有降级：Planner 失败 → 规则计划；向量检索失败 → 仅 BM25；
Reranker 失败 → 保持原顺序；Redis 失败 → 内存模式。

**唯一不降级的是 Verifier**：证据核查失败时宁可整体拒答，
也不放行未经检查的内容。这是系统的底线。

## 三、RAG

### Q7：为什么要混合检索？RRF 是什么？

单路向量检索在金融语料上有两个短板：
1. 查"商誉减值"时，语义相近的"资产减值准备"会被排在前面，但用户要的是商誉；
2. 查"002594"这种代码，在 embedding 空间里没有语义，等于随机召回。

BM25 补上这两点，但它完全不懂"利润质量"和"经营现金流覆盖净利润"是同一件事。

**RRF 公式**：`score(d) = Σ 1 / (k + rank_i(d))`，k=60。

**追问：为什么不用分数加权？**

两路分数分布完全不同：BM25 分数无上界且随语料规模变化，
余弦相似度固定在 [0,1]。要加权就得先归一化，而归一化方式一变，
alpha 的最优值就变，换批语料还要重调。RRF 只用**名次**，天然免疫这个问题。

**追问：k=60 什么含义？**

平滑常数。含义是"名次在 60 以内的差异才显著影响得分"。
k 越小越强调头部名次，越大越平均。60 是 Cormack 原始论文的经验值。

**追问：中文怎么分词？**

优先 jieba，没装则退回"2-gram + 单字"混合。不用纯单字：
单字会让"率""的"这类高频字主导 IDF，区分度大幅下降。

---

### Q8：为什么还要 Rerank？

召回的 top 20 里真正相关的通常只有 3~5 条。全塞给 LLM 有两个坏处：
token 成本翻四倍，噪音稀释注意力导致引用到不相关的条目。

**Bi-Encoder vs CrossEncoder**：
- Bi-Encoder（召回用）：query 和 document 分别编码再算相似度，
  两者之间**没有交互**，所以能预计算、能建索引，但精度有限；
- CrossEncoder：把 (query, document) 拼成一条输入过一遍模型，
  每个 query token 都能注意到每个 document token，精度显著更高，
  代价是**没法预计算**，必须对每个候选实时算。

所以是"粗排 20 条（快）→ 精排 5 条（准）"的两阶段设计。

**追问：模型选型有什么问题吗？**（主动说，显得诚实）

`ms-marco-MiniLM-L-6-v2` 是英文 MS MARCO 数据集训练的，
对中文精排弱于 `bge-reranker-base`。这里为了体积做了取舍
（80MB vs 1.1GB，演示环境友好）。生产环境应该换。
这一点我在代码注释和 README 的"已知局限"里都写了。

## 四、MCP

### Q9：MCP 是什么？为什么用它？

Model Context Protocol，Anthropic 提出的工具接入标准协议。
通过 JSON-RPC 2.0 暴露两个核心方法：`tools/list`（列出工具）、
`tools/call`（调用工具）。

**为什么用**：Agent 直接 `import` 工具模块会产生硬编码依赖——
新增数据源要改 Retriever 代码，工具定义散落在两处，远程工具接不进来。
MCP 让 Agent 只面向协议编程。

**追问：你用的是官方 SDK 吗？**

没有，只实现了协议层，传输层用进程内调用。
官方 SDK 面向 stdio/SSE，会引入 asyncio 事件循环和子进程管理，
而我的工具是同步的（AKShare + pandas），套一层 async 传输
只是把阻塞挪进事件循环，没有实际收益。

关键是我把协议层和传输层**拆开了**：
`handle_request` 完整实现了 JSON-RPC 语义和标准错误码，
将来把它挂到 stdio 或 HTTP 端点上就变成真正的远程 Server，工具代码一行不改。
可以现场演示 `POST /api/mcp/financial_data` 这个调试路由。

**追问：Agent 是走 JSON-RPC 还是直接调？**

直接调（`execute_tool_call`）。协议的价值在于"工具怎么被发现和描述"，
这一点通过 `get_openai_tool_definitions()` 已经体现了。
把 `ToolResult` 转成 MCP 字典再转回来是无谓的序列化损耗。

另外有个设计细节：`BrokerToolRegistry` 把 Broker 伪装成 `ToolRegistry`，
让 `AgentLoop` 保持只认识一种协作方——否则 AgentLoop 里会出现
"要么用 registry 要么用 broker"的分支，破坏单一职责。

## 五、评测

### Q10：怎么评测一个 Agent？

四个维度，但**只有一个用 LLM**：

| 维度 | 权重 | 方式 |
|------|------|------|
| factual_accuracy | 40% | LLM-as-Judge，逐条判定 expected_facts 是否被覆盖 |
| refusal_calibration | 30% | 确定性：该拒答时有没有输出具体数字（正则扫描） |
| evidence_coverage | 20% | 确定性：已验证结论 / 总结论 |
| retrieval_efficiency | 10% | 确定性：从 trace 读轮次和工具命中率 |

**追问：为什么只有一个用 LLM？**

能算的都算出来，只在真正需要语义判断的地方用 LLM，
这样**评测本身的方差**才可控。同一份输出两次评测给出不同分数，
这个评测就没有意义。

**追问：Judge 怎么保证稳定？**

三件事：
1. 用 deep 层 + temperature=0；
2. 要求**逐条判定**而不是整体打分——逐条能列出 matched/missing，
   失败时可直接定位；整体打分只能得到一个不知道从何改起的数字；
3. **不信任 LLM 自己算的 score**，用 judgements 列表在代码里重算。
   模型做除法出错的概率不低，而这个分数直接决定评测结论。

**追问：拒答题怎么评？**

不评事实准确性——预期就是"什么都别说"，
用事实覆盖率去评会得出"覆盖率越低越好"的荒谬结论。
这类题直接把拒答校准分复用为事实准确性分。

拒答校准的判定是确定性的：扫描研报里有没有"带亿/万/% 的数值"
（排除年份和股票代码），有就判 0 分。用"有没有输出数字"
而不是"语气像不像拒答"，因为幻觉的危害在于给出了错误数字，不在于措辞。

### Q11：跑出来分数怎么样？遇到过什么失败？

（跑完真实评测后填入具体分数）

主动讲三个真实失败（`eval/failure_log.md`）：

1. **F-001 列名漂移**：AKShare 新浪财报接口在部分标的上返回
   "一、营业总收入"（带序号前缀），硬编码 `df["营业收入"]` 拿不到，
   `KeyError` 被宽泛的 except 吞掉，退化成 None，
   结果是研报里所有金额显示"—"但**没有任何报错**。
   修复：三段式列名匹配 + 显式别名表 + 收窄 except。

2. **F-002 容差过宽**：见 Q4。

3. **F-003 压缩破坏消息配对**：`ContextCompact` 把发起 `tool_calls` 的
   assistant 消息压掉了，但对应的 `role=tool` 消息因为"保留所有工具结果"
   的规则被留下，形成孤儿消息，API 返回 400。
   修复：把带 tool_calls 的 assistant 也算作"携带证据"，
   另加一道 `_repair_tool_call_pairing()` 兜底。

**这三个的共同点**：都是"静默失败"——不报错，只是结果变差。
这类问题只有靠 trace 复盘才能发现，这也是我坚持自建可观测性的原因。

## 六、可观测性

### Q12：出了问题怎么排查？

每次运行落盘 `traces/run_{run_id}_{时间戳}.json`，包含：
- `summary`：总耗时、token、LLM 调用次数、工具调用次数（含失败数）、
  门禁检查次数（含拦截数）、节点路径；
- `events`：每一步的事件（`llm_call` / `tool_call` / `gate_check` /
  `compact` / `node_enter` / `node_exit` / `retrieval`），
  带输入输出摘要（截断 200 字符）、耗时、token、success 标记。

能直接回答："哪一步慢"、"哪个工具挂了"、"哪句话被门禁拦了、为什么"。

**追问：为什么不用 LangSmith？**

需要外部服务和账号，演示环境跑不起来；
而且"自建可观测性"本身就是这个项目想展示的能力之一。
另外 trace 的 schema 是我按业务需要设计的——
`gate_check` 事件和它的 `gate_status` 元数据是这个项目特有的，
托管方案给不了。

**追问：摘要截断 200 字符会不会丢信息？**

会，但完整内容留在 metadata 里（可选，默认不存）。
工具返回的财务报表动辄几万字符，全存会让 trace 文件比研报本身大两个数量级，
而且没人会去读。需要完整数据时看缓存文件（`data/tool_cache/`）。

## 七、生产工程

### Q13：FastAPI 里怎么跑同步的 Agent？

这是个陷阱题，答错说明没真部署过。

研究流程整条是同步阻塞的（AKShare 是 requests，
sentence-transformers 是 CPU 密集）。直接在 `async def` 路由里调
会**卡死事件循环**——所有其他请求包括健康检查全部无响应。

**处理**：`anyio.to_thread.run_sync` 丢到线程池。

另外提供两种模式：同步（CLI/评测用）和异步 + SSE（Vue 前端用）。
后台任务用 `asyncio.create_task` 而非 `BackgroundTasks`——
后者在响应发送**之后**才执行，而我需要"立即返回 session_id 时任务已在跑"。

**追问：create_task 有什么坑？**

返回的 task 没有强引用可能被 GC 中途回收。
我用 `_BACKGROUND_TASKS` 集合持有引用，完成后由 done_callback 移除。

---

### Q14：为什么要 API 层？Vue 不够吗？

Vue 只负责演示：提交问题、SSE 看节点、渲染研报。Agent、门禁、模型都在 FastAPI 进程里。

- UI 崩溃不应带走研究流程；
- 评测脚本和 curl 必须能调同一套接口；
- 现场演示：`python main.py --api` 打开 `/` 就是 Vue；调试用 CLI。

没有第二套 Web（已去掉 Gradio），避免被问「为什么要两套界面」。

---

### Q15：Redis 用来做什么？没有 Redis 能跑吗？

两个用途：
- 会话状态（TTL 1 小时）：研究要跑 30~120 秒，HTTP 同步等会超时，
  需要地方存进度让客户端轮询。用 Redis 而非进程内字典是因为多 worker 部署下
  "请求打到 worker A，轮询打到 worker B"会查不到。
- 工具结果热缓存（TTL 10 分钟）：与磁盘冷缓存（content-hash，1 天）互补。

**能跑**。Redis 连不上时会话降级为进程内字典、缓存降级为纯磁盘，
并在 `/api/health` 里如实报告 `degraded` 状态。
缓存是性能优化，不是功能依赖；让缓存故障演变成服务故障是错误的耦合。

**追问：为什么 tools/cache.py 是同步的、session/cache.py 是异步的？**

因为工具执行链路整条是同步的，没法 await。
两套客户端读写**同一套 key 格式**（`tool:{tool_name}:{content_hash}`，
由同一个 `make_cache_key` 生成），缓存内容互相可见。
这个设计成立的前提是复用同一个 key 生成函数，不能各写各的。

## 八、金融业务

### Q16：这个 Agent 懂金融吗？

**所有金融计算都在代码里，不交给 LLM**：
毛利率、ROE、杜邦拆解、同比增速、七条风险规则。
LLM 只负责解释"为什么变化"，不负责计算"变化了多少"。

**理由**：LLM 做算术不可靠且错得没规律，评测里表现为随机失分。
而且有些"常识"它经常搞错：
- 上期为负（亏损）时算同比增速，用有符号分母会让"亏损收窄"变成负增长
  → `growth_rate()` 里分母取绝对值；
- "增速放缓"（+42%→+29%）不等于"下滑"
  → `classify_trend()` 用两期增速的符号和大小关系显式区分；
- 比率变动要用**百分点**不是百分比（17.1%→18.5% 是 +1.4pp，不是 +8.2%）。

**追问：举个业务规则的例子**

风险规则里的"应收账款增速 > 营收增速 × 1.5"。
但我在知识库里同时写了**反向情形**：
收入季节性集中在 Q4 导致期末应收自然偏高、
主要客户是政府/央国企回款周期长但信用风险低、
公司主动从预收款转向账期以拓展大客户——
这三种情况触发规则但不构成风险。

规则给出信号，判断要结合行业特性。研报里会把两边都呈现出来。

**追问：银行和制造业能用同一套指标吗？**

不能，这是知识库要解决的问题之一。举两个：
- 资产负债率：制造业 70% 是预警线，银行天然 90%+，
  那是"吸收存款"的负债经营模式决定的，评价银行杠杆要看资本充足率；
- 毛利率：银行没有"营业成本"科目，毛利率概念无意义，要看净息差。

评测里第 7 题就是这个陷阱题：
"平安银行资产负债率 90% 以上是不是杠杆过高"——
合格的回答必须**纠正问题的错误前提**，而不是顺着说"是的风险很大"。

---

### Q17：前视偏差是什么？为什么重要？

用在分析基准日**尚未公开**的数据去支撑历史判断。
例如以 2025-03-01 为基准日，却引用 2024 年年报（3 月 28 日才披露）——
基于此得出的任何结论都不成立，因为当时的人不可能知道这些数据。

这在回测和投研里是能让整套结论作废的错误。

**实现**：`Evidence` 强制带 `disclosure_date`（必填字段，不是可选 metadata），
门禁第 2 级检查 `disclosure_date <= claim.as_of_date`，
不通过判 `lookahead_blocked` → ❌拒答。

**追问：披露日期哪来的？**（主动暴露局限）

数据源没给，我用**法定截止日估算**（年报=次年 4/30，中报=当年 8/31）。
这是个已知局限（F-006）：真实披露日可能是 3/28，
基准日落在 3/28 到 4/30 之间时会**误拦**一条本可用的数据。

**为什么不改**：获取真实披露日要爬交易所公告，成本远超收益。
而且这个偏差方向是**保守的**——宁可误拦一条合规数据，
也不能让未来数据混进历史分析。在投研场景里这两种错误的代价不对称。

## 九、开放性问题

### Q18：如果给你更多时间，会改什么？

按优先级：

1. **换中文 reranker**（`bge-reranker-base`），
   现在的英文模型是明确的短板，改动量小、收益直接。
2. **支持季度分析**。现在只取年报，因为指标体系全是同比口径，
   混入季报会让同比变环比。要正确支持需要"同比期匹配"逻辑
   （2024Q3 对 2023Q3），这是个独立功能。
3. **同业对比**。现在的风险阈值是通用口径，
   "资产负债率 70%"对不同行业含义差很多。
   接入行业分类 + 可比公司数据后，能把绝对阈值换成分位数判断。
4. **真实披露日期**。爬交易所公告，消除 F-006 的误拦。
5. **评测集扩到 30 题**。9 题的统计意义有限，
   单题波动会明显影响总分。

### Q19：这个项目最难的地方是什么？

不是任何单个技术点，而是**在多个都"能跑"的方案里选一个**，
并且能说清为什么。

具体举一个：证据门禁的容差设计。
一开始用统一的 5% 相对误差，跑起来完全正常，评测分数也不低。
直到我手工核对一份研报，发现"毛利率 22.9%"被判为已验证，
而真实值是 21.8%——1.1 个百分点，在投研上是完全不同的结论，
但相对误差刚好 5.0%，卡在容差内通过了。

这类问题不会报错，评测也未必抓得到（LLM Judge 可能觉得"差不多"），
只能靠对业务的理解去发现。修复方式是按数字语义分三档容差。

**这件事让我明白**：Agent 项目的难点在于"静默失败"——
系统看起来在正常工作，输出也像模像样，但内容是错的。
对抗它的办法是把尽可能多的判断从概率模型挪到确定性代码里，
再用 trace 让每一步都可复盘。
