# 架构说明

这份文档解释**每个技术选择背后的权衡**，而不是重复代码里已有的说明。
每一节的结构是：面临什么问题 → 有哪些选项 → 选了哪个 → 代价是什么。

---

## 1. 分层：哪些自建，哪些用框架

### 问题
Agent 项目最容易走两个极端：全部用框架（LangChain 一把梭，出问题不知道从哪查），
或者全部自建（三个月写了个半成品 LangGraph）。分界线怎么画？

### 决策
分界线画在 **"通用问题" vs "领域特有问题"**：

| 层 | 做法 | 理由 |
|----|------|------|
| 编排（谁在什么条件下跑） | LangGraph | 状态合并、条件回边、递归保护都是标准化问题，成熟方案够用 |
| 运行时（单个 Agent 内部怎么跑） | 自建 Harness | max_turns 策略、压缩时机、证据门禁是本项目的差异化，藏进框架就没法改也没法讲 |
| 工具协议 | MCP（自实现协议层） | 协议本身是标准，但官方 SDK 绑定 stdio/asyncio 传输，与同步的 AKShare 不匹配 |
| LLM 调用 | 自建 httpx 客户端 | DeepSeek 有非标字段（reasoning_content、cache_hit_tokens），SDK 拿不到 |
| 向量库 | Chroma | 本地持久化模式，无需额外服务进程 |

### 代价
- 自建 Harness 意味着 LangChain 生态的现成组件（callbacks、memory）用不上，
  需要自己实现 trace 和上下文管理。这部分大约 800 行代码。
- 收益是：出问题时整条链路都能读懂，且每个策略点都可以单独调整和讲清楚。

### 反例：如果全用 LangGraph
`create_react_agent` 能三行代码起一个 ReAct Agent，但：
- max_turns 耗尽时它抛异常，而本项目需要"返回部分结果 + 降级研报"；
- 上下文超限时它直接报 API 错误，没有"保留工具结果、只压缩对话"的策略；
- 证据门禁根本无处安放——它不是 LangGraph 的概念。

## 2. 证据门禁：为什么不用 LLM 自查

### 问题
如何判断"这句话有没有证据支撑"？

### 选项
| 方案 | 问题 |
|------|------|
| 让 LLM 自查（self-critique） | 用非确定性系统校验非确定性系统，幻觉会叠加；模型对自己的输出天然自信 |
| 子串匹配（数字在原文出现过就算通过） | 原文里的 7771 可能是别的指标；漏掉单位换算；无法处理"营收 7771 亿"vs"777102000000 元" |
| **LLM 抽取 + 代码判定** | 选这个 |

### 决策
职责切分：
- **LLM 负责抽取**（自然语言 → 结构化断言 + 数字），这是它擅长的；
- **代码负责判定**（数字比对、日期比较、来源等级），这是确定性计算。

关键点是数字的**语义归属**由抽取方负责：LLM 要指明
`{metric: "gross_margin", value: 0.218, kind: "ratio"}`，
而不是让门禁去原文里正则找数字——"毛利率从 17.1% 提升到 21.8%"
有两个数字，正则无法知道哪个是本期。

### 容差分档
一刀切 5% 会让比率类校验形同虚设。见 `harness/evidence_gate.py` 的 `_compare()`：

```
绝对值  → 5% 相对误差   （7771 亿 vs 7770 亿，容忍四舍五入）
比率    → 0.5 个百分点  （21.8% vs 22.9% 相对误差 5%，但结论完全不同）
增速    → 1 个百分点
```

### 检查顺序
代码里的顺序是 **来源 → 时点 → 口径 → 数字**，与 md 描述的
"来源 → 数字 → 时点"不同。原因：如果一条证据本身构成前视偏差，
它的数字对不对已经无关紧要，先做时点过滤能给出更准确的失败归因
（报 `lookahead_blocked` 而不是先在数字级通过再被时点否掉）。
对外表现的四种状态与规格完全一致。

## 3. 混合检索：为什么 RRF 而不是分数加权

### 问题
BM25 和向量检索的结果怎么合并？

### 选项对比

**分数加权**：`final = alpha * vector_score + (1-alpha) * bm25_score`

问题在于两路分数的分布完全不同：
- BM25 分数无上界，且随语料规模和文档长度变化；
- 余弦相似度固定在 [0,1]。

要加权就得先归一化，而归一化方式（min-max / z-score / softmax）一变，
alpha 的最优值就变。换一批语料还要重调。

**RRF**：`score(d) = Σ 1 / (k + rank_i(d))`

只用**名次**，不用分数。天然免疫分布差异，没有需要调的超参
（k=60 是原始论文的经验值，含义是"名次在 60 以内的差异才显著影响得分"）。

### 决策
用 RRF。保留 `alpha` 参数作为两路的**可信度权重**（默认 0.5 时退化为标准等权 RRF），
应对"知识库很小时 BM25 更可靠"这类场景。

### 中文分词
BM25 需要分词。优先用 jieba（若已安装），否则退回 **2-gram + 单字**混合切分。
不用纯单字切：单字会让"率""的"这类高频字主导 IDF，区分度大幅下降。

## 4. 上下文压缩：与 TradingAgents 的区别

### TradingAgents 的做法
用 `RemoveMessage` 把历史整体清空，只保留最终结论。

### 为什么本项目不能这么做
TradingAgents 的每个 Agent 输出一段独立观点，下游只需要观点本身。
本项目的下游（Verifier）需要**回溯原始数字做证据校验**——
清空历史等于丢掉证据链。

更微妙的问题：即使是"摘要"也不行。工具结果里的
"营业收入 777,102,000,000 元"一旦被摘要成"营收约 7771 亿"，
证据门禁在比对时会因为精度损失而判定失败，
本该 ✅已验证 的结论会被降级成 ⚠️未验证。

### 决策
四步策略，核心是第三步：
1. system prompt 不压
2. 最近 3 轮不压
3. **所有工具结果不压**
4. 更早的过程性对话（LLM 的中间推理文本）交给 quick 模型摘要

### 踩过的坑
压缩会破坏 `tool_calls` ↔ `tool` 消息的配对关系，导致 API 返回 400。
处理方式是两道防线：`_is_evidence_bearing()` 把带 `tool_calls` 的
assistant 消息也算作证据予以保留；`_repair_tool_call_pairing()` 做兜底清理。
详见 `eval/failure_log.md` 的 F-003。

## 5. MCP：为什么保留协议但用进程内传输

### 问题
md 要求用 MCP，但官方 SDK 面向 stdio/SSE 传输，会引入 asyncio 事件循环
和子进程管理，而本项目的工具是同步的（AKShare + pandas）。

### 决策
把 MCP 拆成**协议层**和**传输层**，只实现协议层：
- 协议层：`tools/list`、`tools/call`、JSON-RPC 2.0 消息格式、标准错误码
  → 完整实现（见 `mcp_servers/base_server.py` 的 `handle_request`）
- 传输层：进程内方法调用，不走 stdio/HTTP

这个拆分让"将来改成真正的远程 Server"变成一个纯增量改动：
把 `handle_request` 挂到 stdio 或 HTTP 端点上即可，工具代码一行不改。

### 双接口
同时提供两套接口：
- `handle_request(dict) -> dict`：完整 JSON-RPC 形态，
  用于演示协议、以及 `/api/mcp/{server}` 调试路由；
- `execute_tool_call(ToolCall) -> ToolResult`：Python 原生调用，
  Agent 走这条，省掉一层无意义的序列化。

两者共用同一份 `ToolRegistry` 实现，不会出现"协议层能用、直调不能用"的分裂。

### 适配器
`BrokerToolRegistry` 把 `MCPToolBroker` 伪装成 `ToolRegistry`，
让 `AgentLoop` 保持只认识一种协作方。否则 AgentLoop 里会出现
"要么用 registry 要么用 broker"的分支，破坏它的单一职责。

## 6. 金融计算：为什么全部交给代码

### 决策
毛利率、ROE、杜邦拆解、同比增速、七条风险规则，
全部在 `data/schemas.py` 和 `tools/compare_periods.py` 里用代码实现。
LLM 只负责**解释**"为什么变化"，不负责**计算**"变化了多少"。

### 理由
1. LLM 做算术不可靠，且错得没有规律——评测里表现为随机失分，无法定位；
2. 这些公式是确定的，代码实现后同一份数据永远算出同一个结果；
3. 有些"常识"LLM 经常搞错，例如：
   - 上期为负（亏损）时算同比增速，用有符号分母会让"亏损收窄"变成负增长
     （`growth_rate()` 里分母取绝对值）；
   - "增速放缓"（+42% → +29%）不等于"下滑"，但 LLM 经常混用
     （`classify_trend()` 用两期增速的符号和大小关系显式区分）；
   - 比率变动要用百分点不是百分比（17.1% → 18.5% 是 +1.4pp，不是 +8.2%）。

### 代价
新增一个指标要改代码，不能靠改 prompt。这是刻意的：
指标定义属于业务规则，应该被版本管理和评测覆盖，不该藏在 prompt 里。

## 7. 异步与阻塞：FastAPI 里怎么跑同步 Agent

### 问题
FastAPI 路由是 `async def`，但研究流程整条是同步阻塞的
（AKShare 是 requests，sentence-transformers 是 CPU 密集）。
直接在 async 路由里调 `pipeline.run()` 会卡死事件循环——
所有其他请求（包括健康检查）全部无响应。

### 决策
所有阻塞调用用 `anyio.to_thread.run_sync` 丢到线程池。
这是 async 框架里跑同步代码的唯一正确姿势。

另外提供两种模式：
- `async_mode=false`：等结果返回，适合 CLI 和评测脚本；
- `async_mode=true`：立即返回 session_id，客户端轮询，适合 Web 前端。

后台任务用 `asyncio.create_task` 而非 FastAPI 的 `BackgroundTasks`——
后者在响应发送**之后**才执行，而我们需要"立即返回 session_id 时任务已在跑"。

### 陷阱
`asyncio.create_task` 返回的 task 如果没有强引用可能被 GC 中途回收。
`routes.py` 里用 `_BACKGROUND_TASKS` 集合持有引用，完成后由回调移除。

## 8. 缓存：为什么是两级

### 问题
AKShare 单次调用 2~5 秒，且有隐性频率限制。
开发和评测阶段同一个 `(ticker, periods)` 会被请求几十次。

### 决策
两级缓存：

| 层 | 存储 | TTL | 作用 |
|----|------|-----|------|
| 热层 | Redis | 10 分钟 | 同一会话内的重复查询 |
| 冷层 | 磁盘（content-hash JSON） | 1 天 | 跨会话、跨进程持久化 |

查询顺序：Redis → 磁盘 → 调 AKShare。磁盘命中时回填 Redis。

### 同步 / 异步双客户端
规格里 `session/cache.py` 的 `ToolCache` 是 async 的，
但工具执行链路整条是同步的，没法 await。

处理方式：两套客户端读写**同一套 key 格式**
（`tool:{tool_name}:{content_hash}`，由 `tools.cache.make_cache_key` 统一生成），
缓存内容互相可见。复用同一个 key 生成函数是这个设计成立的前提。

### content-hash 而非手工拼 key
手工拼接的问题是参数顺序、类型（`3` vs `"3"`）、默认值省略与否
都会产生不同的键，命中率会莫名其妙地低。
规范化 JSON（sort_keys + 类型归一）保证语义相同的调用命中同一条目。

## 9. 数据层：AKShare 的三个坑

### 坑 1：列名漂移
同一个字段在不同接口、不同年份下叫法不同：
"营业总收入" / "营业收入" / "一、营业总收入"。
硬编码列名是这类项目最常见的线上故障源。

**处理**：`find_column()` 三段式匹配（精确 → 去序号前缀后精确 → 包含），
配合显式维护的别名表（`INCOME_FIELD_ALIASES` 等）。
别名表按业务优先级排序，保证"净利润"不会被"净利润(扣除...)"抢先命中。

### 坑 2：单位不统一
有的接口返回元，有的返回万元，同花顺系接口甚至返回 `"7,771.02亿"` 字符串。

**处理**：在模型层就把单位固定死——**金额一律为元，比率一律为小数**。
`parse_amount()` 支持中文单位字符串解析。
不在入口统一，后面证据门禁比对时会出现"差了 1e8 倍"的事故。

### 坑 3：报告期 vs 披露日期
2024 年报的报告期是 2024-12-31，披露日期可能是 2025-03-28。
混用会造成前视偏差。

**处理**：`Evidence` 同时带 `period_end` 和 `disclosure_date` 两个字段，
且 `disclosure_date` 是**必填**的（不是 metadata 里的可选键），
让"忘记填"变成构造期错误。数据源没提供时用法定截止日**保守估算**。

## 10. 评测：为什么只有一个维度用 LLM

### 决策
四个维度里只有 `factual_accuracy` 用 LLM-as-Judge：

| 维度 | 方式 | 为什么 |
|------|------|--------|
| factual_accuracy | LLM-as-Judge | "输出是否覆盖了预期事实"需要语义理解 |
| refusal_calibration | 确定性 | 扫描是否输出了具体数字 + 检查拒答标记，正则够用 |
| retrieval_efficiency | 确定性 | 从 trace 读轮次和工具调用，与预期对比 |
| evidence_coverage | 确定性 | 已验证结论 / 总结论，直接算 |

能算的都算出来，只在真正需要语义判断的地方用 LLM——
这样评测本身的方差才可控。同一份输出两次评测给出不同分数，
这个评测就没有意义。

### Judge 的两个约束
1. 要求**逐条判定** `expected_facts` 是否被覆盖，而不是整体打分。
   逐条判定能列出 `matched_facts` / `missing_facts`，失败时可直接定位；
   整体打分只能得到一个不知道从何改起的数字。
2. **不信任 LLM 自己算的 score**，用 `judgements` 列表在代码里重算。
   模型做除法出错的概率不低，而这个分数直接决定评测结论。

### 拒答题的特殊处理
拒答题（用例 8、9）不评 `factual_accuracy`——
预期就是"什么都别说"，用事实覆盖率去评会得出"覆盖率越低越好"的荒谬结论。
这类题直接把 `refusal_calibration` 的分数复用为事实准确性分，
保证加权总分的语义正确。

## 11. 降级策略清单

生产级系统的标志不是"不出错"，而是"出错时行为可预期"。
本项目的所有降级路径：

| 组件 | 失败场景 | 降级行为 |
|------|---------|---------|
| Planner | 结构化输出失败 | 用关键词规则生成计划（`rule_based_plan`） |
| Retriever | 工具超时/失败 | 失败结果回喂给 LLM，让它换工具或说明缺失 |
| Retriever | 循环 max_turns 耗尽 | 返回已获得的证据，状态标记为 `max_turns` |
| Verifier | 断言抽取失败 | **不放行**，全部降级为 ⚠️，Writer 输出拒答研报 |
| Writer | 正文生成失败 | 程序渲染的条目式正文（信息完整性优先于可读性） |
| Writer | 无已验证结论 | 输出拒答研报，说明缺什么数据 |
| 向量检索 | Chroma/embedding 失败 | 降级为仅 BM25 |
| BM25 | 索引构建失败 | 降级为仅向量检索 |
| Reranker | 模型加载/打分失败 | 返回混合检索的原始顺序 |
| 新闻检索 | AKShare 条数不足（<3） | 调 Tavily 补充并合并去重（**补充**而非替代） |
| 新闻检索 | AKShare 失败但 Tavily 可用 | 单走 Tavily，`providers` 字段如实反映 |
| 新闻检索 | 两路都抛异常 | 抛 `DataSourceError`；但"正常返回 0 条"不算失败，只记 note |
| Redis | 连接失败 | 会话降级为进程内字典，缓存降级为纯磁盘 |
| 上下文压缩 | LLM 调用失败 | 规则压缩（保留首句和数字） |
| LLM | 429/5xx | 指数退避重试（2s/4s/8s + 抖动） |
| LLM | 400/401 | **不重试**，直接返回错误（重试只是把同一个错误犯三遍） |

唯一**不降级**的地方是 Verifier：证据核查失败时宁可整体拒答，
也不放行未经检查的内容。这是这个系统的底线。
